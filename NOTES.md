## M2: Automation engine

- **PCRE2 added via FetchContent in M2** (target `pcre2-8-static`, tag `pcre2-10.45`), completing the dependency set alongside Asio/nlohmann-json/Catch2 already fetched in M1. Per the M1 NOTES entry, dependencies are fetched incrementally as each milestone actually needs them rather than all fetched unused from M1.
- **`TriggerOptions`/`AliasOptions` are free namespace-scope structs, not nested inside `TriggerManager`/`AliasManager`.** Both GCC 13.3 and Clang 18.1 reject a nested aggregate struct with default member initializers used as a `= {}` default argument on a *sibling* member function of the same enclosing class (confirmed via a minimal reproduction: `class M { struct O { bool b=false; }; void f(O o={}); };` fails to compile on both compilers with "default member initializer ... required/needed ... before the end of its enclosing class"). Pulling the options structs out to namespace scope (with a `using Options = ...;` alias inside the manager class for a clean call-site name) resolves it with no semantic change. Documented in both headers.
- **Trigger prefilter: per-trigger required-literal substring scan instead of a shared Aho-Corasick automaton.** The spec explicitly allows "a justified simpler multi-substring scan" as an alternative. At the target scale (200 triggers), the simpler approach — each trigger independently checks `line.plain.find(required_literal)` — measured at ~50,000+ lines/sec in this environment (25x the 2,000 lines/sec target) with a corpus mixing matching and non-matching lines, so building and lazily rebuilding a combined automaton wasn't justified by the actual performance need. `extract_required_literal()`'s heuristic and its safety property (never claim a substring is required when the pattern could match without it) are documented in `regex_pattern.hpp` and covered by an extensive test suite in `tests/test_regex_pattern.cpp`, including the specific hazard of a literal run inside an optionally-quantified group being wrongly promoted to "required".
- **Alias regex matching uses full-match semantics; trigger regex matching uses substring/anywhere semantics.** The spec doesn't explicitly state this distinction for aliases. Following the common MUD-client convention (an alias replaces what you typed, so the *whole* typed command should match, not just a substring of it), `AliasManager` compiles regex-kind patterns wrapped as `\A(?:pattern)\z`. Triggers match `StyledLine::plain` per spec text with no such wrapping, matching anywhere in the line, which is the universal convention for trigger patterns (e.g. `you (win|lose)` should fire regardless of what precedes it on the line).
- **Reentrancy safety in `TriggerManager::process_line` and `AliasManager::expand_recursive`.** Neither M2 component has Lua wired in yet, but both `Action`/`FunctionAction` callback types are designed so that in M3 a Lua callback can freely call back into the same manager (e.g. `client.remove_trigger(id)` from inside a trigger's own callback) without holding a stale reference/iterator into a `std::vector` that a nested `add_trigger`/`remove_trigger` call might reallocate or shrink. Both methods snapshot the ids to process before running any callback and re-look-up each entry by id immediately before use. **Critic round 1 (M2-F2) found that `AliasManager::expand_recursive` invoked the callback through a still-live pointer into the vector (`a->action`) instead of copying the action out first the way `TriggerManager::process_line` does** — safe as long as the callback's own registrations never forced a reallocation, but a real heap-use-after-free (reproduced under ASan) once it did. Fixed by copying `Action action = a->action;` (and the `fall_through` flag) out before invoking. The regression test was also strengthened to actually force a reallocation (500 aliases registered from inside the callback) rather than the original single-add version, which never exercised the bug.
- **ASan caught a real stack-use-after-return bug in `bench/trigger_bench.cpp` itself** (not library code): a local `int fired` counter was captured by reference into a lambda stored inside `TriggerManager` past the end of the function that declared it. Fixed by removing the (unnecessary, since `TriggerManager::MatchOutcome::fired_count` already reports this) per-trigger counter. Left as a NOTES entry since it's good evidence the ASan job is actually exercising the code, not just building it.
- **`command_parser` validates only shape (arity/subcommand-name), not semantics.** `#connect <host> <port>` is accepted with any two tokens; whether the host resolves, the port is numeric, etc. is the dispatcher's job. Full dispatch into `NetworkClient`/`TimerManager`/`TriggerManager`/`AliasManager`/Lua is engine wiring, which per spec scope belongs to M3 (`main.cpp`, headless mode) alongside `script_engine`. `command_parser` is deliberately usable and fully tested standalone ahead of that wiring.

- **M2 Critic round 1: REQUEST_CHANGES with 3 blocking + 1 non-blocking finding (`reviews/m2-round1.json`).** All three blocking findings were real bugs, independently reproduced by the Critic against the pristine (unmutated) code, and are now fixed:
  - **M2-F1** (`extract_required_literal()` trimmed only one *byte*, not a whole UTF-8 codepoint, before a `*`/`?`/`{` quantifier — since patterns compile with `PCRE2_UTF|PCRE2_UCP`, an optional multi-byte character like an emoji could leak its leading byte(s) into a "required" literal, violating the prefilter's core safety property). Fixed with a `pop_last_utf8_codepoint()` helper that walks back over UTF-8 continuation bytes to the lead byte before trimming. Regression test added (`tests/test_regex_pattern.cpp`, "an optional multi-byte UTF-8 codepoint is trimmed whole, not by one byte").
  - **M2-F2** (`AliasManager` reentrancy gap — see the entry above).
  - **M2-F3** (mutation-testing gap: the M1→M2 fix for a CI-flaky pause/resume test, which paused immediately at registration to eliminate the flake, incidentally removed the only test scenario able to exercise `TimerManager`'s generation-counter check, so deleting that check entirely passed the whole suite). Fixed by adding a dedicated race test that deliberately re-introduces the timing race (pausing just before a very short repeating timer's own deadline) but discriminates correct-vs-buggy behavior by watching for several multiples of the tick interval afterward: a correct implementation produces at most one stray tick and then silence, while removing the generation check produces a continuous cascade of ticks at the timer's interval (since the stale completion keeps rescheduling itself) — a difference of about an order of magnitude that holds regardless of how fast the test happens to execute (verified stable under both `release` and the substantially slower `asan` preset, and confirmed to fail clearly — leaked ticks roughly 4-5x over threshold — with the mutation re-applied).
  - **M2-F4** (HANDOFF.md's embedded SHA lagging its own tip by one commit, the same pattern as M1-F1) is left as-is for the same reason as M1-F1: it's a historical record of the review conversation, the Critic verified the actual tip's CI independently, and the only diff between the cited and actual commit is HANDOFF.md itself.

## M3: Scripting

- **Lua/sol2 dependencies added in M3.** Lua 5.4.7 (official source tarball from lua.org, no CMake support upstream, so compiled ourselves as a static library excluding `lua.c`/`luac.c`; hash-pinned) and sol2 v3.5.0 (bumped from an initial v3.3.0 while investigating the bug below; the bug reproduced identically on both versions, so the bump wasn't the fix, but there's no reason to go back to the older release). Completes the dependency set from `docs/SPEC.md`'s tech stack, per the incremental-fetch policy from the M1/M2 NOTES entries.
- **Deferred coroutine resume via a pump queue, to work around a real crash.** `client.wait_for`/`client.sleep` (the coroutine-based test API) need a trigger or timer callback to `coroutine.resume()` a suspended test coroutine. Calling `coroutine.resume()` **directly inside** a callback that C++ invokes through a stored `sol::protected_function` (i.e. from inside a trigger/timer callback dispatched by `TriggerManager`/`ScriptEngine::dispatch_timer`) reliably segfaults — reproduced down to a minimal case (see below) — specifically when the coroutine being resumed had yielded from a *nested* Lua function call (e.g. `wait_for`'s own stack frame) rather than directly from its top-level function. AddressSanitizer traced it to a wild read inside Lua's own `resume()` (`ldo.c`), consistent with the resumed coroutine's internal call-info chain being corrupted. The *identical* `coroutine.resume()` call succeeds every time when made from a **fresh top-level script invocation** (another `sol::state::safe_script` call), rather than from inside an already-running `protected_function` call.
  Minimal repro (isolated by bisecting away pieces of `wait_for` until only the essential shape remained): a coroutine created and first-resumed from a top-level chunk, whose body calls a *separate* Lua function that does `coroutine.yield()` and, from a `client.register_trigger` callback fired later via `ScriptEngine::dispatch_line`, resumes it — crashes. The same structure with the resume moved to a second top-level `run_string` call — does not crash. Neither the timer path, nor self-removal of the trigger from within its own callback, was necessary to reproduce it; nesting the yield inside a helper function plus resuming through the C++-invoked-callback path was the whole story.
  Given real-world Lua code uses exactly this "yield from a helper, resume from an external event's callback" pattern constantly (it's the standard coroutine-scheduler idiom), this looks like a genuine interaction bug between sol2's `protected_function` call mechanism and Lua's coroutine resume machinery in this specific nested-yield shape, rather than a Lua limitation — but root-causing it further inside sol2/Lua's C internals was out of scope for the time available. Worked around architecturally instead: `wait_for`/`sleep`'s callbacks call `client._queue_resume(co, value)` (pushing onto a plain Lua table) instead of resuming directly; every `ScriptEngine::dispatch_*` method calls `pump_resumes()` immediately after running any trigger/timer/event-handler callbacks, which runs `client._pump_resumes()` as its own fresh top-level `safe_script` call — matching the call shape that's been reliable in testing (117 tests, 5 repeated full runs under ASan with no failures, including the specific coroutine-based test-API tests that would have hit this directly). Documented in code at `ScriptEngine::pump_resumes()`'s definition.
- **`extract_required_literal` limitations, sandbox scope, etc. carried forward from M2 are unaffected by M3.**
- **`client.wait_for`'s underlying trigger is registered with `match_prompts = true`, unlike `TriggerManager`'s own default of `false`.** Discovered while validating the replay/live-test fixture below: the mock server's login prompt (`"Enter (c)reate or (v)isit: "`) has no trailing newline, so it's only ever delivered as a *prompt* line (via `NetworkClient`'s 250ms idle-flush, `TelnetParser::flush_idle`/`complete_line(is_prompt=true)`), which `TriggerManager::process_line` skips for a trigger with `match_prompts = false`. Permanent triggers default to skipping prompts (so they don't fire repeatedly against unchanging prompt text like `HP:100>`), but `client.wait_for` is a one-shot wait for a specific, arbitrary piece of text — often exactly an unterminated prompt (a login banner, a "press any key" line) — so defaulting it to match prompts too is the correct behavior for that API, not a workaround. Fixed in `kBootstrapLua`'s `wait_for` definition (`src/script_engine.cpp`).

- **Until then, `tests/live/zombiemud.lua` and `tests/replay/zombiemud_session.jsonl` are a clearly-marked synthetic placeholder**, built against a small local mock MUD server (used only during development, not committed) that models the same shapes a real MUD session exercises: an unterminated login prompt (`"Enter (c)reate or (v)isit: "`), a room description with an ANSI SGR color (`"\x1b[32mTown Square\x1b[0m"`), a repeating "Obvious exits:" line, a line meant to be gagged (`"This is a secret gagged debug line N"`), a refused-move error (`"You can't go that way."`), and a clean disconnect (`"Goodbye!"`). The script's header comment quotes every mock-server line each pattern/trigger is traceable to, mirroring the spec's real-recording requirement in form (traceability + quoted source lines) even though the source itself is synthetic. It exercises: `client.wait_for` (twice, including the prompt-matching fix above), `client.send`/`sent_log` verifying alias expansion (`e4`/`s3` → 4x `east`/3x `south`, and that the alias names themselves never reach `sent_log`), `client.sleep`, `register_timer`/`pause_timer`/`resume_timer`/`kill_timer`, `register_trigger` with `gag = true`, a plain (non-gag) trigger, and `client.on('line')` span color inspection. Exits 0 on success, 1 with `FAIL: ...` lines on any check failure.
- **`tests/fake_mud`** is a small test-only replay server (linked against `mudclient_core` only for its `base64_decode` helper): given a recorded JSONL session via `--record`, it listens on `--port` (or an ephemeral port, printing `PORT <n>` to stdout so the orchestrator can discover it), accepts one connection, and replays each recorded entry's inbound bytes at (roughly, scaled by `--speed`) their original inter-arrival timing, non-fatally logging (not failing) a mismatch on an expected outbound line — the replay only needs to reach the right synchronization points, not byte-for-byte reproduce the original client's timing.
- **`tests/run_replay_test.py`** orchestrates the two binaries: starts `fake_mud` on an ephemeral port, points the real `mudclient` binary at it via the `MUD_HOST`/`MUD_PORT` env override (which `main.cpp` only honors in `--test` mode, per the M3 CLI design), runs it with `--test tests/live/zombiemud.lua`, and propagates its exit code as the ctest result. Wired into `tests/CMakeLists.txt` as ctest `replay_zombiemud`, requiring `find_package(Python3 COMPONENTS Interpreter)`. Verified passing under both the `release` and `asan` presets (118/118 tests green in both, including this one).
- **Connection-refused/timeout-before-login is a skip, not a failure (spec section 5).** `tests/live/zombiemud.lua` tracks whether a `disconnect` event ever arrives before a `connect` event; if the login-screen `wait_for` then times out under that condition, it echoes `SKIP: server unreachable` and exits 0 rather than reporting the login check as failed. This distinguishes "the real server is genuinely unreachable" (not this client's fault) from "the server is live but slow/broken" (a real failure) using events the client already fires, with no new client API needed.
- **Found and fixed a real process-shutdown hang while validating `scripts/init.lua` against the mock server.** `main.cpp`'s shutdown sequence posted `network->disconnect()` then relied on `network_work_guard.reset()` + `network_thread.join()` to let the network thread's `io_context::run()` return. This works only when there's no other outstanding async work; a script's own still-armed repeating timer (`client.register_timer(..., true, ...)`, e.g. `scripts/init.lua`'s example 5s tick) is itself pending async work independent of the guard, so `run()` correctly kept waiting for that timer's next deadline instead of returning, and `network_thread.join()` hung indefinitely (reproduced: process only exited after being killed with SIGKILL, well past its own `--timeout`). Fixed by having the same posted task call `network_io.stop()` right after `disconnect()` — `disconnect()` is fully synchronous (cancels its own timers, shuts down and closes the socket) so ordering the two in one posted lambda still gets a clean socket close first, and `stop()` then makes `run()` return immediately, abandoning any other still-pending handlers (fine, since the process is exiting anyway). No regression: 118/118 tests still green under both `release` and `asan` after the fix.
- **`scripts/init.lua`** ships the example the spec asks for: a 5s repeating timer echoing a tick counter, and a trigger on `^(\w+) (hits|misses) you` that echoes an ANSI-colored message (`client.echo` writes its argument straight to the terminal, so embedding a raw SGR escape in the Lua string is how a script styles its own output — there's no separate "styled echo" API). Manually verified against a small mock combat-line server.
- **windows-msvc CI caught two real issues in this milestone's first push.** (1) `std::getenv` under `/W4 /WX` is a hard build failure on MSVC (C4996, "may be unsafe"); fixed by wrapping the two read-only call sites (`MUD_HOST`/`MUD_PORT` test-mode overrides) in a tiny `get_env()` helper with a locally-scoped `#pragma warning(disable : 4996)`, rather than disabling it project-wide. (2) `TimerManager: repeating timer fires multiple times, killed timer stops` flaked on a loaded Windows runner (`count_fires_within(events, 100ms) == 0` saw 1) — the same inherent asio race already documented and accepted for pause()'s generation-counter test (`kill()`'s posted task can lose a race against a completion that was already dispatched before it ran; `kill()` erases the entry outright, so there's nothing left to reschedule from, meaning at most one stray tick, never a cascade). Loosened the assertion to `<= 1` to match that established precedent, rather than trying to eliminate an asio limitation that can't be eliminated from this layer; a genuine "kill doesn't work" regression would still produce a continuous stream of ticks at the 20ms interval within the 100ms window, which the loosened assertion still catches.
- **`live-test.yml`/`release.yml` added per spec section 7.** `live-test.yml` runs on a weekly schedule, `workflow_dispatch`, and `workflow_call`; it captures the live-test binary's actual exit code into a step/job output (rather than relying on `continue-on-error`'s step outcome, which a reusable-workflow caller can't observe) so `release.yml` can report pass/fail in its release notes. `release.yml` builds+tests+packages on Linux x86_64/aarch64 and Windows x64, computes `SHA256SUMS`, attests build provenance, calls `live-test.yml`, and publishes the GitHub Release. All newly-added third-party action SHA pins (`upload-artifact`, `download-artifact`, `attest-build-provenance`) were verified against upstream tags via `git ls-remote --tags` (outbound HTTPS/git access works from this environment even though raw TCP to zombiemud.org:3000 does not) — this caught one transcription typo in an initial `upload-artifact` pin before it was committed.

- **M3 Critic round 1: REQUEST_CHANGES with 1 blocking + 3 non-blocking findings (`reviews/m3-round1.json`).** M3-F1 (blocking: synthetic, non-real live-test fixture) is a genuine environmental blocker, independently reproduced by the Critic from its own environment — escalated via `ESCALATION.md` rather than disputed or claimed fixed. M3-F2 (major, security: tag-derived version interpolated into a workflow `run:` instead of `env:`) fixed in `release.yml` (now `env:` + `shell: bash` + `"$MUDCLIENT_VERSION"`). M3-F3 (minor, correctness: unescaped/unvalidated id/duration splices into synthesized Lua for built-in commands) fixed with new `is_valid_number()`/`lua_id_or_label()` helpers in `main.cpp` — incidentally also fixed a latent bug where a bare numeric timer id at the prompt was always treated as a label lookup instead of an id lookup. M3-F4 (minor: `#timer reset`/`#timer list` unwired) partially fixed: added `client.reset_timer()` and wired `#timer reset`; `#timer list` left as a known limitation (no `TimerManager` enumeration API; judged out of proportion to a minor, self-disclosed, untested finding for this round). The Critic's own adversarial test (`tests/critic/critic_lua_sandbox.cpp`, testing whether the instruction-budget hook reaches a runaway loop hidden inside a nested `coroutine.create()`/`resume()`) wasn't wired into the build yet; wired it in and ran it — both cases pass (the hypothesis is disproven: `lua_sethook` on `lua_.lua_state()` covers the shared `global_State` that every coroutine off it also runs under), so the test's own comments (which asserted the opposite) were corrected to match the actual, safe result and it's kept as a permanent regression test.
